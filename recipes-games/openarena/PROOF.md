# OpenArena 0.8.8 - pins, sizes, measured rounds

Numbers are kept here, out of the README, so the README stays one screen of
instructions. Everything below is what the build in the image and the seat rounds
actually did.

## The payload

```
https://download.tuxfamily.org/openarena/rel/088/openarena-0.8.8.zip
  425,189,255 B, sha256 5a8faf7f5b51f351b0a1618c06b6b98a5f1a6758f1d39818de2c87df2a0bac4a
LICENSE "GPL-2.0-or-later", COPYING md5 94d55d512a9ba36caa9b7df079bae19f (GNU's own v2 text)
PV 0.8.8    PKGR r0.01    S ${WORKDIR}/openarena-0.8.8
```

`openarena.ws` hands out this release through a download form whose link now
302-redirects through the Internet Archive, so the form is not a stable fetch
address. The archive's own target is the tuxfamily address above, which is still
served today and answers with the release's own metadata (`Content-Length
425189255`, `Last-Modified` Feb 2012), and the site's file page publishes 395.51
MB with md5 `9f353d96d7889c377349d692c3905e5b` for this very file - this round
re-fetched it and agrees with both. The sha256 below was taken by fetching that
URL and hashing what came down, so a changed asset fails `do_fetch` rather than
shipping something else. The deb version has to start with a digit for dpkg, and
the release is named `0.8.8`, which does.

The licence is the one the release itself states: `readme_088.txt` inside the zip
has a LICENSE section that reads "The program and data are licensed under the GNU
GPL v2. See the file 'COPYING' for details.", and `COPYING` at the top of that
same zip is the 17,992-byte GNU v2 text with GNU's own md5 `94d55d512a9ba36caa9b7df079bae19f`.
That is the whole claim, program and data both - and it is the reason one free
download is enough here: the assets are free-to-use under the same v2 the engine
is under, not only free to fetch.

## What the zip holds, and what the package installs

The zip unpacks to a directory named after the release, and the payload inside
it is two sibling directories:

| Tree | Content | Bytes |
| --- | --- | --- |
| `baseoa/` | nine pk3s, `pak0` .. `pak6-patch088` | 410,218,649 B |
| `missionpack/` | one pk3, `mp-pak0.pk3` | 6,250,219 B |

`missionpack` is kept as a sibling rather than merged, so a map inside it stays
addressable by its own name, and the same client reads it as a second game
directory. The rest of the zip is what the same release ships for other platforms
(the macOS `.app` bundles, the Windows `openarena.exe`, the readmes and the
credits), and this recipe installs none of it.

This round's deb is `openarena_0.8.8-r0.01_arm64.deb`, 403,636,880 B, md5
`788b1b02a473ec1dac2e2574b5463f1d`, 11 payload files: the ten pk3s and the
launcher. The previous round's data manifest, `/tmp/opencode/manifests/openarena.txt`
on the build host with md5 `73acc115f837df4b0c8bac46637b5424` for the whole tree
and 416,469,563 B, is what the seat's own tree was verified against, and this
round's ten pk3s are the same bytes because nothing about the payload moved.

The modes are spelled out because the payload arrives as a `cp` of the extracted
zip: `unzip` leaves the directories at 700 and the files at 644 owned by whoever
runs bitbake, a 700 directory is not world-readable - which is what the seat
answers "Failed to open dir /usr/share/openarena/baseoa/" with - and the uid is
what `do_package_qa` calls host contamination. The install puts the dirs at 0755
root:root and the pk3s at 0644.

The launcher is one more installed file: `/usr/bin/openarena` 1,157 B md5
`37c3c028af16f2d8824972bff23c7300`, generated by `do_install:append`; this round
the seat got it as one extracted file from the deb's own `data.tar.xz` and a
`md5sum` on the seat agrees with that md5. It runs
`-basedir /usr/share/openarena -game baseoa -quake3` with
`OPENARENA_ARGS` defaulting to `-set vid_gl_context_es 1 -set vid_fullscreen 1
-set vid_width 1024 -set vid_height 576`, and it takes the map as arguments.
There is no `pr_ssqc_memsize` here: that arena belongs to the Quake-C progs the
Quake payload ships, and the Quake III gamecode has none.

## The engine side is FTEQW's, not this recipe's

FTEQW carries the Quake III engine code **compiled in, not loaded**: `config_fteqw.h`
has `-DLINK_QUAKE3`, `engine/Makefile:142` resolves `LINK_QUAKE3=1` and links
`../plugins/quake3` plus botlib straight into the binary, and `engine/common/plugin.c:66`
registers `{"quake3", Plug_Q3_Init}`. Running the client prints
`------- Quake III Arena Initialized -------`. FTEQW's own table of named games has
no OpenArena entry, so the launcher states `-quake3` by hand and `-game baseoa`
only names the tree - which protocol and which data are therefore both explicit
on the seat, nothing is guessed. `-updatesrc ""` has to stay on both the Quake
and the OpenArena runs.

The one engine edit this game needs is not in this recipe either: OpenArena's
`qagame.qvm` calls the `G_REAL_TIME` game trap with a null `qtime`, which FTE's
pointer validator rejected before the trap body ran, and
`0002-quake3-real-time-accept-null.patch` in the fteqw recipe's `files/` is what
let the game past `Call to game trap 41 passes invalid pointer` - see
`../fteqw/README.md`.

```
/usr/bin/openarena +wait 3 +map oa_dm6

  log proof (WAYLAND_DEBUG=1):
            Setting mode 1024*576 32bpp OpenGLES2+
            wl_surface@19.damage(0, 0, 1024, 768)
            xdg_toplevel@26.set_fullscreen(wl_output@13)
            lock_pointer x1, relative_pointer_v1 relative_motion x2
            Initing default SDL audio device.
  fps: 53.5 steady over the measured 20 s
  cost while it ran (from /proc, 6 s apart): 77 % of one core, rss 161688 kB
  ps beside it: VSZ 894736 KB  RSS 161836 KB  %CPU 95.0
  free -m while it ran: 1768 total, 571 used, 1196 available
```

The fps is counted the same way for both games - the `wl_surface@19.commit()`
lines of the game's own surface in the `WAYLAND_DEBUG=1` log, over the steady
20 s that starts 12 s in - and on OpenArena it swings far more than on LibreQuake.
The whole ladder on the seat, steady 20 s over `oa_dm6`, with the surface the
seat actually allocated:

| Ask | Surface | `oa_dm6` steady fps |
| --- | --- | --- |
| `vid_fullscreen 2` (1920x1080) | 1920x1080 | 22.1 |
| 1280x720 | 1280x720 | 40.5, 42.7, 43.4, 46.5, 48.1, 48.4, 52.1, 56.2 (median 47) |
| 1024x576 (shipped) | 1024x768 | 49.5, 50.2, 51.9, 53.5, 53.6, 64.7 (median 52) |
| 768x432 | 800x600 | 53.8, 54.0, 54.2 |
| 640x360 | 640x480 | 52.6, 79.2 |

So the same curve as LibreQuake's: the seat is fill-rate bound and the buffer
area is the lever, and OpenArena's real gain runs from 22 fps at the seat's own
desktop size to about 52 at the shipped 1024x576 - below that the game stops
paying (768x432 measures about the same as 1024x576), while LibreQuake still
gains there. OpenArena's spread is bot-side work, not measurement noise: the
same setting measured 40.5 and 56.2 in two runs, so only tiers this far apart
are real.

The same round ran the map again with the launcher installed from the deb's own
bytes. The seat's tree is a verified `cp` rather than a `dpkg -i`, because the
403 MB deb plus its extraction does not fit on a filesystem that is 91 % used
(4271 MB total, 403 MB free) with the 398 MB tree already in place. The
verification is a `md5sum -c` of the deb's own payload manifest run from `/`,
which answers OK for all the payload files - so the bytes the recipe installs
and the bytes the seat plays are one and the same.

## The Q3 gamecode's failure modes, measured here

| Symptom | Cause |
| --- | --- |
| a double `+map` or `-set sv_listen_q3 1` segfaulting the client, `rc=139` | both measured on the seat: a launcher with a default map plus a user's own, and the listen-server switch, crash the Q3 gamecode; the launcher has no default map, and the map comes in as `+wait 3 +map <name>` |
| `Unable to resolve server address "local"` from `+connect local` | this build's q3 code has no built-in local-server alias |
| `+status` prints `0 teams with 0 entities` for a single-player map | the Q3 status is a team-matches status, so the Q3 proof is the `SpawnServer:`/`AAS initialized.` lines plus the screenshot, where the Q1 proof can use the full `+status` block |
| `Call to game trap 41 passes invalid pointer` at startup | OpenArena's `qagame.qvm` calls `G_REAL_TIME` with a null `qtime`, which is legal and which FTE's `VALIDATEPOINTER` used to reject - the engine's `0002-quake3-real-time-accept-null.patch` is the answer, not something this data recipe can answer |
| a black frame from a bare `+map` (a 6121-byte black screenshot, the game silent) | `+map` queued before the renderer is up. `+wait 3 +map` loads every time; one `+wait` delays one frame (see the fteqw recipe's note: `engine/common/cmd.c:206` `Cmd_Wait_f` waits a single `rframe` and ignores its argument) |

## The Q2 search this payload's rule ended

The rule this layer plays by is that a game needs to be free to use AND free to
download before it gets a data recipe, and OpenArena passes both, which is why it
is the second data recipe. The Quake II search stopped on the licence half, and
the stop is recorded so the search does not restart: the yamagi downloads are
source archives of the client plus the CTF/Reckoning/Ground Zero addon source
packages, and every one of them still wants id's paks - there is no fully free
Q2 asset set, so no Q2 recipe and no further search.
